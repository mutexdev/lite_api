--- US-076 — stale workspace pointer across the runner's lock release (FIXED) ---
  A real, silent data-loss bug, confirmed by negative control rather than by
  reading. sendRequestWithControlsContext captured `ws` — a *Workspace pointing
  INTO the a.state.Workspaces backing array — released a.mu for the network
  round trip, re-acquired it, and then handed that same pointer to
  applyScriptVariableContextToState. Any append that grew Workspaces past
  capacity while the lock was free moved the backing array, after which the
  write landed in memory nothing reads. No error, no crash: the variable simply
  vanished.

  THE FIX WAS ALREADY SITTING THERE, DISCARDED. The line that re-acquires the
  lock already re-resolved the collection:
      _, collection, err = a.findCollectionWithWorkspaceIndexedLocked(...)
  It threw the freshly-resolved workspace away with `_` and kept using the stale
  one. Keeping it is the entire fix.

  MEASURED by negative control (stale pointer restored, then reverted):
    with the bug: global variable set by a post-response script -> ""  (lost)
    with the fix: -> "survived", and still present on a fresh GetState
  The bug only bites when a script marks GLOBAL variables dirty, because that is
  the only branch of applyScriptVariableContextToState that dereferences the
  workspace at all. The test drives bru.setGlobalEnvVar for exactly that reason.

  WHY -race NEVER CAUGHT IT, and never would: both accesses are correctly
  serialised under a.mu. Nothing is racing. The pointer is simply stale. This is
  worth remembering — a clean -race run says nothing about pointer lifetime
  across a deliberate lock release.

  Two tests, deliberately of different kinds: a behavioural one that forces the
  reallocation inside the I/O window (the httptest handler creates 8 workspaces
  while a.mu is free), and a source-level guard. The behavioural test only fails
  when the reallocation actually happens, which depends on slice capacity and
  could quietly stop being true if the fixture changes shape — leaving the bug
  uncovered with the test still green. The guard fails the moment the captured
  pointer reappears at the call site, whatever the fixture looks like.

--- US-019 — INVESTIGATED, NOT STARTED. Read this before implementing it. ---
  Analysis done so the next iteration does not repeat it. Two of the story's
  criteria are not equally achievable, and the difference matters.

  1. "sync.Pool of pre-warmed runtimes, reset between uses" — LIKELY INFEASIBLE
     AS WRITTEN, and the story does not acknowledge why. Nearly every shim
     installed by newScriptRuntimeWithMeta CLOSES OVER PER-REQUEST STATE. From
     the signatures alone:
         installScriptFetch(runtime, vars)
         installScriptProcess(runtime, loop, meta.CollectionPath,
                              scriptVars.ProcessEnv, sandboxMode)
     plus reqObject's ~15 getters/setters, which capture item, vars, reqState
     and a currentRequestURL closure over item.Params/item.PathParams.
     A pooled runtime therefore cannot be "reset" cheaply — every global would
     have to be re-installed, which is the entire cost being avoided. Worse, a
     miss leaks the PREVIOUS request's url/headers/env into the next script,
     which is a correctness and secrets-leak failure, not a performance one.
     US-018 already banked the large win here (compiled *goja.Program cache,
     ~10x, 8.2x fewer allocs). What remains is object construction, and pooling
     it is not obviously safe.

  2. "One runtime instead of four where hooks share scope" — ACHIEVABLE, and is
     the real story. But it is 4 -> 2, not 4 -> 1, and the reason is structural:
        runPreRequestScript*        runs BEFORE the request exists as a
                                    response; response = Response{}, and its
                                    whole job is to mutate the outbound request.
                                    It CANNOT share a runtime with the others.
        runPostResponseScript*   \
        runPostResponseVariables  >  all run AFTER, with the same item,
        the tests runtime        /   response, jar and meta. THESE three can
                                    share one runtime.
     That is also closer to Postman, where state set in a post-response script
     is visible to tests.

  SEQUENCING HAZARD if implemented: runPostResponseVariables sets globals into
  its runtime — every combined variable by name, plus $bru and $req. Sharing a
  runtime makes those visible to the tests script, so the order the three run in
  becomes observable behaviour where today it is not. Decide and pin the order
  in a test before writing the refactor, not after.

  The "no variable or cookie state leaks between requests — explicit test"
  criterion should be written FIRST, as a failing test, since it is the one that
  catches every way this can go wrong.

--- US-014 — narrow-return mutators (PASSED, except browser QA) ---
  HEADLINE, measured on the 500-request fixture by marshalling both return
  values the way Wails does:
    one keystroke:  AppState 4,348,018 bytes  ->  narrow 8,515 bytes   (511x)

  Four narrow variants added beside the existing wide ones, which are untouched
  and still work — the story explicitly allows unmigrated callers. Each pair
  shares an extracted ...Locked core rather than duplicating the mutation, so
  the two entry points CANNOT drift. Drift is the failure that matters here: not
  "the narrow one is broken", which shows up at once, but "the two disagree",
  where frontend and backend hold different ideas of what the user typed and
  neither looks wrong.

  THE NO-OP CASE nearly broke the whole design. MoveOpenTab against the end of
  the tab bar mutates nothing and so does NOT bump the revision. The first
  gap-detection rule required exactly (held + 1), which would have classified
  every clamped tab drag as a missed update and fired a full AppState refetch —
  the exact cost this story removes, arriving through the mechanism meant to
  prevent it. Rule now accepts held or held+1, refetches on a skip AND on a
  revision going backwards (a response overtaking a newer one).

  BEHAVIOUR CHANGE in MoveOpenTab: offset 0 against a NON-EXISTENT tab used to
  return success, because the offset check came before the lookup. It now
  reports "tab not found". The narrow variant has to know whether the tab exists
  to return a meaningful result, and reporting success for a tab that is not
  there was wrong either way.

  TEST DESIGN NOTE: the anti-drift test first used two separate apps and had to
  normalise away FilePath and CreatedAt, which differed only because the temp
  dirs and clock readings differed. Every normalised field is a field where real
  drift can hide, so it was rewritten to drive both variants against THE SAME
  item on THE SAME app — leaving exactly one field to normalise (UpdatedAt,
  which both deliberately set to time.Now()).

  Frontend merge logic lives in src/lib/narrowMutations.ts so it is testable;
  10 new tests, almost all about results that must NOT be applied. A narrow
  result patched onto a stale copy is worse than a stale copy: the patch lands,
  the view looks freshly updated, and the stale parts stay stale forever.

  MIGRATED: patchRequest (the keystroke path) and all four tab call sites.
  NOT MIGRATED, deliberately: the two UpdateRequest calls in the
  variable-tooltip editor, each immediately followed by SaveRequest, which
  returns a full AppState anyway — narrowing them would add branching for zero
  saving.

  STILL OPEN: "Verify in browser using browser tools".

--- US-013 — independent dirty scopes for secrets and OAuth2 (PASSED) ---
  Half of this story was already done: US-012 had added a content compare to
  writeEnvironmentSecretsLocked (its comment even names US-013). What remained
  was the OAuth2 file, which had NO gating at all — storeOAuth2Credentials runs
  on every state persist and reads oauth2.json, DECRYPTS every stored
  credential, re-encrypts every merged credential, and writes.

  DESIGN CHOICE worth recording: the story says "each get an independent dirty
  flag", which reads as classifying the 81 markDirty call sites by which files
  they touch. Rejected. A misclassification there does not fail loudly — it
  silently stops persisting a user's secret or a refreshed token, and no test
  in this suite would catch it. Gated on a CONTENT FINGERPRINT instead, which
  cannot be wrong by construction: the write is skipped exactly when the bytes
  would be identical.

  The OAuth2 gate hashes (baseline, local), not local alone. The merge is a
  delta of local against baseline, so a key in baseline and absent from local
  is a DELETION — a revoked token. Hashing local alone makes that identical to
  "never existed", and the skip would swallow the revocation. There is a test
  for exactly this.

  Skipping is SAFE UNDER MULTIPLE WINDOWS in both scopes, and the direction is
  what makes it safe: if another window rewrote the file, our fingerprint still
  describes content identical to what we would write, so skipping leaves their
  newer file intact. Writing is the operation that could clobber.

  MEASURED, same host and settings (-benchtime=200x -count=3), by stashing the
  change and re-running:
    BenchmarkMarkDirty   before 67,484 ns/op  3,078 B/op  26 allocs
                         after  48,742 ns/op  2,290 B/op  24 allocs   (1.38x)
    BenchmarkPersistLockedSmallState  before 5,916,580  after 5,888,383 ns/op
                         — unchanged, and NOT a failure of the OAuth2 gate:
                         that benchmark is ~80% fsync (documented in bench.txt)
                         and its fixture holds zero OAuth2 credentials, so
                         there is nothing to decrypt. Allocations do drop 85->77.
                         The OAuth2 saving scales with credential count, which
                         this benchmark deliberately does not exercise.

  HONESTY NOTE ON THE TESTS: TestSecretsFileIsNotRewrittenByUnrelatedMutations
  would ALSO pass before this story, because US-012's byte compare already
  skipped the write. It is a contract guard, not evidence for US-013. The
  evidence for US-013's secrets half is the benchmark above and nothing else.
  Said so in the test's own doc comment rather than letting it look like proof.

--- US-021 + US-022 — push live WebSocket / gRPC events (PASSED) ---
  The push alone would NOT have fixed the quadratic cost, and the story text
  reads as though it would. Emitting each event incrementally is necessary but
  not sufficient: responseLocked still re-marshalled the whole event log, still
  base64'd it, and still stored it into item.Response inside AppState on every
  single message. Adding an emit on top of that is pure addition.
  So the fix has two halves, and the second is the one that removes the O(n^2):
    1. PUSH   — "ws:event" / "grpc:event", one event each, via EventsEmit.
    2. BOUND  — the response body carries only the last 200 events.

  MEASURED, by negative control (reverted after measuring):
    unbounded body   44,367 B at message 150 -> 88,142 B at message 300  (+98.7%)
    bounded body     29,375 B at message 150 -> 29,385 B at message 300  (+0.03%)
  Doubling the message count doubled the old body exactly as quadratic cost
  predicts. The residual 10 bytes is encoding/json rendering time.Time with
  variable fractional-second width, not a leak — which is why the test asserts
  a 1% bound rather than exact equality, with the reason written down.

  BEHAVIOUR CHANGE, deliberate and documented in session_event_push.go:
  reopening a request whose session ran past 200 events shows the last 200
  rather than all of them. The live UI stays complete because the frontend
  accumulates the pushes; the headers report the true total and the omitted
  count, so nothing is hidden silently.

  Every append routes through appendEventLocked (20 sites, was 20 raw appends).
  That is what makes "no event can be added without being pushed" structural
  rather than a convention. Negative control: reverting ONE site back to a raw
  append fails TestWebSocketEmitsEveryAppendedEvent ("got 6 pushes for 5 sends").

  FRONTEND: a bare append would have been wrong. A listener attaching
  mid-session starts at a non-zero index, and appending blindly yields a log
  that LOOKS complete and is silently missing its beginning — worse than showing
  nothing, because the user cannot tell. Pushes therefore carry index+total, and
  a log is authoritative only when contiguous from 0 and at least as long as the
  body window; otherwise the inspector falls back to the body. Same
  detect-a-gap-and-resync contract as AppState.Revision. 9 new frontend tests.

  Emission happens under session.mu on purpose: the callers already hold that
  lock across a full network round trip (WriteMessage then ReadMessage under a
  read deadline), so a webview notify does not change the critical section's
  shape, and emitting after the unlock would let goroutines interleave and
  deliver events out of order.

  STILL OPEN on these two stories: "Verify in browser using browser tools".

--- US-008 — AppState.Revision (PASSED) ---
  markDirty alone was NOT a sufficient hook, contrary to the obvious reading of
  the story. It covers 81 mutation sites, but 13 more real mutations call
  persistLocked directly for synchronous durability — collection imports,
  collection recovery, draft-guard saves, and the readiness normalisation inside
  ensureReadyLocked. Bumping only in markDirty would have left those silent, and
  silence is the dangerous direction: the frontend concludes it is in sync when
  it is not, and shows stale data forever.
  Resolution: persistLocked split into persistLocked (bump + write) and
  writeStateLocked (write only). persistOnce and flushPersistLocked moved to
  writeStateLocked because they DRAIN a mutation markDirty already counted —
  leaving them on persistLocked would double-count and manufacture a phantom gap.

  The counter lives on App, not inside AppState, and is scrubbed by
  stateForStorage. Both are deliberate; see the doc comments. Three paths
  restore a whole earlier AppState (two collection-import rollbacks, the
  OpenAPI-sync rollback) and would have dragged an in-state counter backwards.

  All four tests proven non-vacuous by negative control, each reverted after
  measuring: dropping the markDirty bump fails two of them; dropping the
  stateForStorage scrub fails IsNotPersisted; making GetState bump fails
  DoesNotAdvanceOnReads.
