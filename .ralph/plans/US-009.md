# US-009 — move response bodies out of AppState

**Status: SCOPED, not started.** Blast radius measured so the next session can
size it before committing.

## Measured blast radius

| surface | count |
|---|---|
| `.Body` references in `app.go` | 202 |
| `BodyBase64` in `app.go` | 12 |
| Go files touching `BodyBase64` | `app.go`, `response_export.go`, `workspace_fixture.go`, `app_test.go`, `response_export_test.go` |
| test assertions on `Response.Body` in `app_test.go` | 69 |
| frontend files reading `bodyBase64` | `lib/workbench/response.ts`, `lib/workbench/ResponseInspector.svelte` |

The 202 `.Body` figure overcounts — it matches `RequestBody`, `item.Body` and
other unrelated fields — but the 12 `BodyBase64` sites are exact and are the
ones the story deletes outright.

## What makes this the risky one

`Response` is persisted inside `AppState`, so changing these two fields changes
the on-disk `state.json` shape. That is why the story requires a versioned
migration following the `workspace_migration.go` pattern, and why a mistake here
loses a user's cached responses rather than merely running slowly.

The 69 existing assertions on `Response.Body` in `app_test.go` are the safety
net: they are what tells you the read path still returns the same bytes after
the body moves behind a handle. Do NOT relax them to accommodate the new shape —
if they need changing, the change is the thing under review.

## Suggested order

1. `responseStore` first, standalone, with its own tests — LRU + spill to
   `<dataDir>/responses/`, no wiring into `Response` yet.
2. Add `BodyHandle` and the inline head ALONGSIDE `Body`/`BodyBase64`, both
   populated. Everything keeps working; nothing reads the handle yet.
3. Migration + loader, verified against a pre-migration `state.json` fixture.
4. Move readers to the handle one at a time.
5. Delete `Body`/`BodyBase64` last, which is when the 69 assertions and the
   frontend's `response.ts` must be updated together.

Steps 1-3 are additive and independently committable. The first destructive
step is 5, and by then the migration has already been proven.

## Related

`response.ts` is a protected asset (improvement_v2.md 2.2) and already has a
characterisation suite from US-038 — 83 frontend tests currently pass. That
suite exists precisely so this rewrite can be shown to preserve behaviour.

## US-010 frontend half — scoped, not started

`ResponseInspector.svelte` currently derives everything from one line:

```
$: rawBody = response?.body ?? ''
```

and five derivations hang off it — `bytes`, `boundedBody`, `pretty`,
`jsonComparison`, plus `display`/`safeDisplay` downstream. The two controls are
pure state toggles today:

```
on:click={() => (renderFull = true)}
on:click={() => (visibleLimit = Math.min(fullRenderLimit, visibleLimit + automaticPreviewLimit))}
```

They are synchronous because `response.body` already holds everything. Moving
them onto `ReadResponseBody` makes them **async**, which is the actual work:

1. Introduce a local buffer, e.g. `fetchedBody`, seeded from `response.bodyHead`
   and extended by `ReadResponseBody(handle, offset, length)`.
2. Point `rawBody` at the buffer rather than at `response.body`, so all five
   derivations follow without individual changes.
3. Reset the buffer when `responseIdentity` changes — the component already
   tracks that for scroll restoration, so reuse it rather than adding a second
   identity.
4. Advance by the returned `Offset`/`Length`, never by the requested length.
   The Go tests already pin why: a multi-byte body trims bytes off the rune
   boundary, and a caller advancing by what it asked for skips them.
5. Keep the tiered limits exactly as they are — 128 KB automatic, 512 KB
   embedded, 1 MB full. They now bound how much is FETCHED, not how much of an
   already-present string is shown, which is the point of the story.

**Do this before US-009 step 5, not after.** Once `Body` is deleted the
inspector has no fallback, so the fetch path must already be proven. The
83-test characterisation suite from US-038 exists to show the rewrite preserves
behaviour — run it against every intermediate state, not just the final one.
