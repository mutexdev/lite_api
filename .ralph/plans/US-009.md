# US-009 — move response bodies out of AppState

**Status: SCOPED, not started.** Blast radius measured so the next session can
size it before committing.

## Measured blast radius

| surface | count |
|---|---|
| `.Body` references in `app.go` | 202 |
| `BodyBase64` in `app.go` | 12 |
| Go files touching `BodyBase64` | `app.go`, `response_export.go`, `workspace_fixture.go`, `app_test.go`, `response_export_test.go` |
| test assertions on `Response.Body` in `app_test.go` | 69 |
| frontend files reading `bodyBase64` | `lib/workbench/response.ts`, `lib/workbench/ResponseInspector.svelte` |

The 202 `.Body` figure overcounts — it matches `RequestBody`, `item.Body` and
other unrelated fields — but the 12 `BodyBase64` sites are exact and are the
ones the story deletes outright.

## What makes this the risky one

`Response` is persisted inside `AppState`, so changing these two fields changes
the on-disk `state.json` shape. That is why the story requires a versioned
migration following the `workspace_migration.go` pattern, and why a mistake here
loses a user's cached responses rather than merely running slowly.

The 69 existing assertions on `Response.Body` in `app_test.go` are the safety
net: they are what tells you the read path still returns the same bytes after
the body moves behind a handle. Do NOT relax them to accommodate the new shape —
if they need changing, the change is the thing under review.

## Suggested order

1. `responseStore` first, standalone, with its own tests — LRU + spill to
   `<dataDir>/responses/`, no wiring into `Response` yet.
2. Add `BodyHandle` and the inline head ALONGSIDE `Body`/`BodyBase64`, both
   populated. Everything keeps working; nothing reads the handle yet.
3. Migration + loader, verified against a pre-migration `state.json` fixture.
4. Move readers to the handle one at a time.
5. Delete `Body`/`BodyBase64` last, which is when the 69 assertions and the
   frontend's `response.ts` must be updated together.

Steps 1-3 are additive and independently committable. The first destructive
step is 5, and by then the migration has already been proven.
