# US-001 — PR CI workflow

Lane: tooling. Reviewers: R1. Depends on: US-002 (`npm test`), US-003 (golangci-lint),
US-004 (`npm run lint`), US-007 (agreed Wails version).

## Goal

Give the repo a pull-request gate. `release.yml` triggers only on push to `main`, so today a
regression is discovered *after* merge, during a release build that also signs and notarises.

## Problem this addresses

`release.yml` runs `go test` / `go vet` / `npm run check` / `npm run build` on three platforms, but
only as a precondition to packaging, and only post-merge. Nothing runs `go test -race`, and until
US-002 nothing ran the 7 frontend test cases at all.

## Files

- **created** `.github/workflows/ci.yml`
- **not touched** `.github/workflows/release.yml` — it stays the release path. CI deliberately
  duplicates a few of its gates rather than refactoring both onto a shared composite action; that
  refactor is a bigger change than this story and would put the release path at risk.

## Design

Three jobs, run in parallel:

| Job | Runner | Gates |
|---|---|---|
| `go` | ubuntu-24.04 | `go build`, `go vet`, `go test ./...`, `go test -race ./...` |
| `go-lint` | ubuntu-24.04 | `golangci-lint run` (US-003) |
| `frontend` | ubuntu-24.04 | `npm run check`, `npm run lint` (US-004), `npm run build`, `npm test` (US-002) |

Decisions worth recording, because they are not obvious from the story text:

1. **`-tags webkit2_41` on every Go command.** Wails links GTK3 + WebKit2GTK. `release.yml`
   already uses this tag for its Linux job. Without it, CI compiles a different program than the
   one shipped, so a green CI would not mean what it appears to mean. The apt dependency install
   is copied from `release.yml` for the same reason.
2. **`-race` is its own step, not merged into the test step.** Phase 1 turns 83 synchronous
   `persistLocked` calls into a background writer (US-012) and converts `a.mu` to `sync.RWMutex`
   (US-020). Those are exactly the changes that produce data races, so a race failure has to be
   attributable on its own rather than hidden behind a functional failure in the same step.
3. **golangci-lint version is pinned** (`v2.12.2`), not floating. The linter gates the build; a
   new upstream release adding a check should be an explicit, reviewable bump rather than a
   surprise red build on an unrelated PR.
4. **`concurrency` with `cancel-in-progress: true`.** Superseded pushes to a PR branch stop
   burning runners. `release.yml` deliberately uses `cancel-in-progress: false` — cancelling a
   half-finished notarisation would be worse than letting it complete.
5. **Ubuntu only.** `release.yml` covers macOS and Windows on the release path. Gating every PR on
   three platforms triples cost for little signal, since these gates are platform-independent.

## Acceptance criteria — how each is demonstrated

| Criterion | Demonstration |
|---|---|
| Triggers on `pull_request` | `on: [pull_request, workflow_dispatch]`; parsed and confirmed via `yaml.safe_load`. |
| Runs build, vet, test, race | Steps `Build`, `Vet`, `Test`, `Test with race detector` in job `go`. |
| Runs `npm run check` / `build` / `test` | Steps `Typecheck`, `Build`, `Test` in job `frontend`. |
| A deliberately broken PR fails | **Partly open — see below.** |
| Typecheck passes | `npm run check` is a CI step; verified locally at 151 files / 0 errors / 0 warnings. |

## Verification performed

- `yaml.safe_load` parses the file; triggers and all three job step lists confirmed.
- `actionlint` (v1, installed for this story) reports **zero findings** on `ci.yml`.
- actionlint was itself sanity-checked: fed a copy with `runs-on: ubuntu-nope-99.04`, it correctly
  reports `label ... is unknown` on both jobs. So the clean result is meaningful, not vacuous.
- `npm test` exit-code behaviour proven locally: 7/7 pass exits 0; an added failing case exits 1;
  removing it returns to exit 0. A non-zero exit fails the step, hence the job, hence the PR.

## Open item

The criterion "a deliberately broken PR fails the workflow" cannot be fully closed locally — it
needs a real run on GitHub Actions. The repo has a live remote (`git@github.com:mutexdev/lite_api`)
and an authenticated `gh`, so the check is one push away:

```sh
git push -u origin ralph/ci-negative-check
gh pr create --fill --title "TEMP: prove CI fails on a broken change"
gh pr checks --watch
gh pr close --delete-branch
```

This is an outward-facing action on a real repository and has **not** been performed without the
maintainer's go-ahead. Until it is, treat this criterion as evidenced-by-proxy (local exit-code
proof) rather than demonstrated.

## Risks

- `golangci/golangci-lint-action@v9` must accept `--build-tags webkit2_41`; if the action rejects
  the arg, fall back to installing the binary directly and invoking it.
- The `go-lint` job repeats the apt install. If CI minutes matter, fold `go-lint` into the `go`
  job as a fourth step; kept separate here so lint failures and test failures are distinguishable
  at a glance.
