## THE LANDMINE — read before writing any key

Svelte throws at RUNTIME on duplicate keys, and neither `svelte-check`, `eslint`
nor `npm run build` can see it. A wrong key is strictly worse than no key.

**`devToolsNetworkColumnWidths = [80, 70, 180, 300, 110, 100, 80]`** — the value
`80` appears TWICE. Keying by value (`{#each … as width (width)}`) crashes the
DevTools network panel the moment it renders. This list is positional
configuration with no identity other than its position, so **index is the
correct key here**, notwithstanding the story's "keys are stable identities, not
array indices" rule — that rule is about lists of entities, and this is not one.

Apply the same test to every list before keying it: *can two elements ever be
equal?* If yes and there is no id, the key must be a composite, not the value.

CORRECTION to an earlier draft of this plan: I assumed the header rows were
unsafe because repeated HTTP header names are legal. They are not unsafe here.
`networkHeaderRows` is `Object.entries(headers ?? {})` over a
`Record<string,string>` — the map has already collapsed duplicates, so names ARE
unique and `(name)` is correct. Verified by reading the function, not assumed.

## THE SECOND LANDMINE — seven iterated types have NO `id`

This is the finding that overturns the story's own rule, and it was established
by reading `frontend/wailsjs/go/models.ts` rather than assumed:

| type | iterated as | identity available |
|---|---|---|
| `KeyValue` | params, headers, form rows | **none** — `name` repeats (duplicate headers are legal AND editable) |
| `Assertion` | assertion rows | **none** |
| `GrpcMessage`, `WSMessage` | message lists | `name`, which repeats |
| `ClientCertificateConfig` | certificate rows | `domain`, which repeats |
| `ScriptLog` | console output | **none** |
| `RunResult` | runner results | `itemId`, repeats across iterations |

A blanket "use `.id`" would emit `undefined` for every row of these — and
repeated `undefined` is a duplicate key, i.e. the crash. This is the single most
likely way to get US-030 wrong.

**For these lists, INDEX IS THE CORRECT KEY, and the story's "stable identities,
not array indices" rule is wrong here.** The reasoning is not convenience: these
are EDITABLE rows, and the only content-derived key available changes as the
user types. A content key would therefore destroy and recreate the `<input>` on
every keystroke — strictly worse than leaving the block unkeyed, and the exact
opposite of the story's own goal ("input focus is not lost mid-edit").

Types that DO carry `id`: `Variable` `NetworkLog` `CookieEntry` `RequestItem`
`TimelineItem` `Environment` `TerminalSession` `Feature` `ResponseExample`
`Workspace` `OpenTab` `Collection`.

Other stable identity fields: `DevToolsProcessMetric.pid`,
`CollectionProtoFile.path`, `CollectionProtoImportPath.path`, `DotEnvFile.path`,
`FolderConfig.path`.

Resolved shapes: `groups` is `{folder, items}[]` → `(group.folder)`;
`visibleEnvironmentRows` is `{variable, index}[]` → `(row.variable.id)`;
`visibleCookieGroups` is grouped by domain → `(group.domain)`;
`visibleKeyBindingEntries` is `Object.entries(section.bindings)` → `(action)`.

## Verification plan

1. `npx eslint . --rule '{"svelte/require-each-key":"error"}'` → 0.
2. Re-enable `svelte/require-each-key` as an error in `eslint.config.js` and
   delete the US-030 disable comment (US-004 recorded it as owned by this story).
3. `npm run check` 0/0, `npm run lint` 0, `npm test`, `npm run build`.
4. **Browser, non-negotiable** — the duplicate-key failure is runtime-only.
   Drive the app at `localhost:34115` (the Wails dev endpoint that serves the Go
   bindings; vite's 5173 does not) and render every keyed list at least once,
   watching the console for "Cannot have duplicate keys". The DevTools network
   panel, the header tables and the cookie groups are the highest-risk.
5. The story's real user-facing criterion — "input focus is not lost mid-edit
   when a list re-renders" — needs a focused input in a keyed list, a state
   change that re-renders it, then `document.activeElement` compared against the
   input. Assert that explicitly; it is the thing keys exist to fix.
