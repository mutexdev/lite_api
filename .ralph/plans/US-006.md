# US-006 — Large-workspace fixture

Lane: tooling (but lives in the root Go package). Reviewers: R1, R2. Blocks: US-005.

## Goal

A deterministic generator that builds a workspace of **500 requests across 10 collections, at least
3 of them carrying a 5 MB cached response**, so that US-005's benchmarks measure the pathological
case described in `improvement_v2.md` §2.1.B rather than a toy state.

## Verified data model

Confirmed by reading `app.go`:

```
AppState.Workspaces []Workspace
  └ Workspace.Collections []Collection
      └ Collection.Items []RequestItem
          └ RequestItem.Response *Response          // app.go:379
              ├ Response.Body       string          // app.go:631
              └ Response.BodyBase64 string          // app.go:632
```

This confirms the spec's central claim structurally: the root `AppState` transitively reaches every
cached response body, and each body is held **twice**. A 5 MB response therefore costs ~5 MB in
`Body` plus ~6.7 MB in `BodyBase64` (Base64 is 4/3) ≈ **11.7 MB**, and `persistLocked` re-serialises
all of it on every keystroke. The fixture must reproduce this, not approximate it.

## Placement decision — the non-obvious constraint

The US-005 benchmark targets (`persistLocked`, `writeCollectionFilesLocked`, `interpolate`,
`newScriptRuntimeWithMeta`, `executeHTTP`) are **unexported**, so `bench_test.go` must be in
`package main` at the repo root.

That forces the fixture into the root package too. It **cannot** follow the `qa/responsefixture` /
`qa/platformfixture` convention, because those are `package main` binaries under `qa/`, and no
subpackage can import the root `package main` to reach `AppState` / `Collection` / `RequestItem`.
§5.4 of the spec lists the fixture alongside those two, which is misleading on this point.

**Resolution:** the generator is a normal root-package Go file so both benchmarks and any future
tests can call it, with a thin `qa/workspacefixture` binary later if a CLI is ever wanted.

## Files

- **created** `workspace_fixture.go` — `package main`, no build tag.

## API

```go
// largeWorkspaceOptions controls fixture shape so benchmarks can scale it down
// when they need a fast inner loop.
type largeWorkspaceOptions struct {
    Collections       int // default 10
    RequestsPerColl   int // default 50  -> 500 total
    LargeResponses    int // default 3
    LargeResponseSize int // default 5 << 20
    Seed              int64
}

func defaultLargeWorkspaceOptions() largeWorkspaceOptions

// buildLargeWorkspaceState returns a fully populated AppState. Deterministic for
// a given seed: byte-identical across runs, so benchmark numbers are comparable.
func buildLargeWorkspaceState(opts largeWorkspaceOptions) AppState

// newLargeWorkspaceApp returns an *App rooted at dir with the fixture state
// installed, using the same constructor the 456 existing tests use
// (NewAppWithDir, app.go:1220).
func newLargeWorkspaceApp(dir string, opts largeWorkspaceOptions) *App
```

## Determinism requirements

- Seeded `math/rand.New(rand.NewSource(seed))` — never the global source, never `time.Now()`.
- All `CreatedAt` / `UpdatedAt` / `SentAt` from a fixed base instant, not the wall clock.
- Fixed IDs (`fixture-coll-%02d`, `fixture-req-%03d`) rather than `uuid.New()`.

Without these, `persistLocked` benchmark timings vary with body entropy (JSON escaping cost) and the
results are not comparable run to run — which would defeat the whole point of the baseline.

## Body content

`Response.Body` must be **realistic JSON**, not `strings.Repeat("a", n)`. A megabyte of one repeated
byte compresses and escapes unrepresentatively, and `json.MarshalIndent` cost is dominated by escape
scanning. Generate a JSON array of records with mixed strings/numbers/nesting, then set
`BodyBase64 = base64.StdEncoding.EncodeToString([]byte(Body))` so the double-storage is faithful.

## Acceptance criteria — demonstration

| Criterion | Command |
|---|---|
| 500 requests / 10 collections | `TestLargeWorkspaceFixtureShape` asserts 10 collections, 50 items each, 500 total |
| ≥3 with 5 MB responses | asserts exactly 3 items with `len(Response.Body) >= 5<<20` |
| Used by US-005 | `bench_test.go` calls `newLargeWorkspaceApp` |
| Deterministic | same seed twice ⇒ `reflect.DeepEqual` on the marshalled state |
| Typecheck / gates | `go build ./...`, `go vet ./...`, `go test ./...`, `go test -race ./...` |

## Risks

- **Race-detector cost.** 500 requests × 11.7 MB of body means a fixture state of well over 1 GB if
  every request got a large body. Only 3 do; the rest get small (~2 KB) bodies. Keep total fixture
  footprint near ~40 MB or `go test -race ./...` will slow sharply or OOM in CI.
- `persistLocked` writes the whole state to disk; the benchmark must use `b.TempDir()` and account
  for real I/O. Report `-benchmem`.
- Adding a non-test `.go` file to the root package puts it in the shipped binary. Keep it
  dependency-free (stdlib only) and small. If a reviewer objects, moving it to
  `workspace_fixture_test.go` is a one-line change — benchmarks can still use it, since `_test.go`
  files are visible to other `_test.go` files in the same package.
