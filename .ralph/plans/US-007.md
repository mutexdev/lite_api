# US-007 — Resolve the Wails version pin

Lane: tooling. Reviewers: R1.

## Goal

Make `go.mod` and CI agree on one Wails version, and prove `wails build` succeeds on it.

## Verified state

The story text says "CI pins `v2.10.2` (`release.yml:16`); QA docs record `v2.12.0`". That is true
but understates *why* the mismatch survived.

| Source | Version |
|---|---|
| `go.mod:15` — the **library** | `v2.10.2` |
| `.github/workflows/release.yml:16` — `WAILS_VERSION`, the **CLI** | `v2.10.2` |
| Locally installed CLI (`wails version`) | `v2.10.2` |
| Every QA/packaging run recorded in `docs/` | CLI `v2.12.0` |

The QA evidence was produced with:

```
go run github.com/wailsapp/wails/v2/cmd/wails@v2.12.0 build -m -nosyncgomod
```
(`docs/ux/2026-07-19-pre-implementation-audit.md:369`)

`-nosyncgomod` tells the CLI **not** to align `go.mod` to its own version. That flag is precisely
why a v2.12.0 CLI kept producing packages against a v2.10.2 library, and why the drift was never
forced into the open. It is a latent mismatch, not a documentation typo.

Supporting references:
- `docs/ux/2026-07-19-pre-implementation-audit.md:101` — flags the mismatch as needing resolution
  before release.
- `docs/ui-redesign-milestone-ledger.md:117` — a pinned v2.12.0 CLI regenerated bindings, rebuilt,
  packaged and self-signed successfully; concludes the v2.10.2 CLI is "removed from the release
  path".
- `docs/ui-redesign-milestone-ledger.md:94` — the multi-process window model depends on **v2.12**
  exposing one native window per process. This is a behavioural dependency, not just tooling.

`go list -m -versions` confirms available: … `v2.11.0 v2.12.0 v2.13.0`.

## Decision: converge on v2.12.0

Not v2.10.2: the shipped, QA-accepted packaging path is v2.12.0, and the window model depends on
v2.12 semantics. Downgrading would contradict banked evidence.

Not v2.13.0, even though it is newer: every QA result in `docs/` was produced on v2.12.0. Jumping a
minor version would invalidate that evidence for no stated benefit, and this story's job is to
*remove* ambiguity, not introduce a fresh unreviewed variable. A v2.13.0 bump is a legitimate
follow-up with its own QA pass — logged to `.ralph/backlog.md`.

Must run **after** the US-003 worker finishes. Both would otherwise touch `go.sum` concurrently, and

## Steps

```sh
go get github.com/wailsapp/wails/v2@v2.12.0
go mod tidy
go build ./... && go vet ./... && go test ./... && go test -race ./...
go install github.com/wailsapp/wails/v2/cmd/wails@v2.12.0
wails build -nocolour            # must succeed; then launch build/bin/LiteAPI.app
```

## API-compatibility evidence (measured, not assumed)

Both module versions were fetched into an isolated throwaway module and diffed directly, so this is
not inference from a changelog.

LiteAPI imports exactly these Wails packages:

```
github.com/wailsapp/wails/v2
github.com/wailsapp/wails/v2/pkg/menu
github.com/wailsapp/wails/v2/pkg/menu/keys
github.com/wailsapp/wails/v2/pkg/options
github.com/wailsapp/wails/v2/pkg/options/assetserver
github.com/wailsapp/wails/v2/pkg/options/mac
github.com/wailsapp/wails/v2/pkg/runtime
```

Diff of v2.10.2 → v2.12.0 across all of them:

| Package | Result |
|---|---|
| `wails.go` (root) | identical |
| `pkg/menu`, `pkg/menu/keys` | identical |
| `pkg/options/assetserver` | identical |
| `pkg/runtime` | **additive only** — gains `notifications.go`, `signal_linux.go`, `signal_other.go` |
| `pkg/options` (+`mac`, +`windows`) | changed, but **zero removed lines** |

> `diff <v2.10.2> <v2.12.0> | grep '^<'` returns **empty** for every imported package.

**Conclusion: the upgrade is purely additive across 100% of the API surface LiteAPI uses.** No
symbol we call is removed, renamed, or re-signatured. This materially lowers the risk this story
was assumed to carry.

Specifically, the `Screen` struct is byte-identical in both versions: `Width`/`Height` are still
present (still marked deprecated) and `Size`/`PhysicalSize` exist in both. So the
`workspace_window_runtime.go` screen-size code is unaffected by the version choice — the SA1019
finding there is a pre-existing lint issue owned by US-003, **not** an upgrade blocker, and the two
must not be conflated.

## Risks

- The API surface is safe (above), but Wails' **generated bindings and build tooling** are not
  covered by that diff. `wails build` regenerating `frontend/wailsjs/` remains the real risk, and a
  packaged-app launch is still required evidence.
- Regenerated bindings may diff `frontend/wailsjs/`. That directory is generated; a diff is expected
  and must be reviewed, not blindly committed.
- `go mod tidy` may move transitive deps. Review the `go.sum` diff rather than accepting it wholesale.
