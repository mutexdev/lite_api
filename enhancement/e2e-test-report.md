# LiteAPI End-to-End Feature Sweep Report

**Date:** 2026-08-22
**Method:** 15-agent parallel sweep, one agent per functional area. Every issue an agent reported was independently re-verified by a second, skeptical agent (re-reading the source and, wherever possible, reproducing the defect with a standalone throwaway test) before being counted as confirmed.

## Summary

15 functional areas of the LiteAPI app were swept end-to-end. Across all areas, **7 issues were confirmed** by independent re-verification (1 high, 5 medium, 1 low), and **0 reported issues were rejected/refuted** by the verifier this round — every issue that was reported was confirmed. It's worth stating plainly why the confirmed/not-confirmed distinction matters even though nothing was rejected this time: a "not confirmed" verdict means a second, skeptical reviewer could not independently reproduce the claim by reading the code and running a targeted repro — it does not mean the original report was impossible or malicious, only that it didn't clear the bar of independent, reproducible evidence. Treating "reported" and "confirmed" as separate categories keeps low-confidence or environment-specific claims from being silently promoted to accepted defects.

### 1. GraphQL variables sent/logged as a stringified JSON blob instead of a JSON object
- **Severity:** High
- **Area:** Sending requests with different body types (GraphQL)
- **File:** `internal/core/app_execute_http.go` (also `internal/core/app_send.go`)
- **Description:** Two independent GraphQL payload builders in `internal/core` duplicate logic that exists correctly in `internal/codegen/codegen.go` (`GraphQLRequestBodySnapshot`), but both build `map[string]string{"query": ..., "variables": ...}` instead of unmarshalling the variables text into an `interface{}` first. Because the map's value type is `string`, `json.Marshal` always emits `"variables":"{...}"` (a JSON string containing escaped JSON) instead of `"variables":{...}` (a nested JSON object), which is what the GraphQL spec requires.
  1. `internal/core/app_execute_http.go:75-84` — the fallback body-builder that fires whenever `item.Type=="graphql"` but `buildBody()` returned a nil reader (reachable by switching the Body-mode dropdown away from `graphql` for a GraphQL request in the UI). The bytes actually sent over the wire have `variables` as a string, which most GraphQL servers will reject or silently mis-coerce.
  2. `internal/core/app_send.go:539-556` (`networkLogRequestBody`) — runs for *every* GraphQL request (the default `body.Mode=="graphql"` case). This feeds `NetworkLog.RequestBody`, i.e. what the app displays in its Network Log. So for essentially every ordinary GraphQL request with non-empty variables, the Network Log's recorded body diverges from what was actually transmitted, misleading anyone debugging from the log.
- **Repro steps:**
  1. Call `networkLogRequestBody(RequestBody{Mode:"graphql", GraphQLQuery: "query Foo($id: ID!) { foo(id: $id) }", GraphQLVariables: `{"id": "123"}`}, map[string]string{})` and compare its output to `buildBody()` on the same body — they disagree on the type of `"variables"`.
  2. Create a GraphQL-type request, switch Body Mode to `none` while leaving `GraphQLQuery`/`GraphQLVariables` populated, and send — the outgoing POST body has `variables` as an escaped string rather than an object.
- **Verifier's reasoning/confidence:** High confidence. Directly inspected all three files. `codegen.GraphQLRequestBodySnapshot` (codegen.go:110-121) correctly unmarshals `GraphQLVariables` into `interface{}` before marshaling. Both `app_execute_http.go`'s fallback and `app_send.go`'s `networkLogRequestBody` build `map[string]string`, forcing `variables` to serialize as an escaped string. Confirmed the spec violation and the log/wire-body divergence match the report exactly.

### 2. Failed global-environment write leaves in-memory workspace state permanently dirty (no rollback)
- **Severity:** Medium
- **Area:** Postman environment/globals import
- **File:** `internal/core/collection_import_apply.go`
- **Description:** In `ApplyCollectionImport`, the branch handling a detected postman-environment candidate calls `applyImportedGlobalEnvironmentsLocked(workspace, ...)`, where `workspace` is a live pointer directly into `a.state.Workspaces[i]`. That function appends the new `Environment` to `workspace.GlobalEnvironments` and bumps `workspace.UpdatedAt` **before** calling `writeWorkspaceGlobalEnvironmentFilesLocked` to persist to disk. If the disk write fails (permission error, disk full, or the `environments` path being blocked by a non-directory file), the error is reported in `result.Errors`, but — unlike the sibling collection-import branch a few lines below, which explicitly does `a.state = before` plus mutation rollback — this path never restores state. The already-appended environment stays live in memory (and in `result.State`) even though the API told the caller the import failed, and a later unrelated write to global environments would silently complete the write the user was told had failed.
- **Repro steps:**
  1. Create a workspace via `newAppForTest`.
  2. Delete the workspace's `environments` subdirectory and replace it with a regular file, forcing `os.MkdirAll` inside `writeWorkspaceGlobalEnvironmentFilesLocked` to fail.
  3. Preview and `ApplyCollectionImport` a Postman environment file against that workspace.
  4. `result.Errors` has one entry (correctly reported as failed) but `result.State.Workspaces[0].GlobalEnvironments` already contains the new environment — state was mutated without being persisted or rolled back.
- **Verifier's reasoning/confidence:** High confidence. Traced `findWorkspaceLocked` → confirmed it returns a live pointer, not a copy. Traced `applyImportedGlobalEnvironmentsLocked` → confirmed in-memory append happens unconditionally before the fallible disk write. Confirmed the sibling collection-import branch does roll back (`a.state = before`) while this branch does not. Wrote and ran a standalone repro test matching the reporter's exact steps; output matched precisely (one error row, GlobalEnvironments went from 0 to 1 entries). Test file was removed after verification.

### 3. Discovered collections selected/imported by name only — identically-named collections can't be distinguished, and the wrong ones get imported
- **Severity:** Medium
- **Area:** Discovery and import of Insomnia/Bruno/Thunder Client collections
- **File:** `internal/core/app_discovery.go` (also `frontend/src/lib/modals/DiscoveryModal.svelte`)
- **Description:** Both the frontend selection state and the backend's selection matching use the collection's display Name as the sole identity, with no id or index. In `DiscoveryModal.svelte`, `selectionKey(client, name) = "${client}:${name}"` is the checkbox's checked source and write target. If two discovered collections for the same client share a name (e.g. two Insomnia workspaces both still named the default "Untitled"), ticking one checkbox writes to the same state key the other reads from — both show checked/unchecked together, so the user cannot select just one. On the backend, `ImportDiscoveredCollections` builds a `wanted` set from the `names` list and imports every discovered collection whose trimmed Name matches, regardless of how many share that name. There is no per-item preview step before the import call, so this is not a display glitch — selecting one of two identically-named collections silently imports both into the user's workspace with no chance to review or decline the unintended one.
- **Repro steps:**
  1. Have (or simulate) an Insomnia install with two workspaces sharing the same name (e.g. "Untitled").
  2. Open the Discovery modal, expand Insomnia — both entries listed under the same name with independent checkboxes.
  3. Tick only the first one — both checkboxes become checked (frontend), because they read/write the same `insomnia:Untitled` key.
  4. Clicking Import selected calls `ImportDiscoveredCollections(workspaceId, 'insomnia', ['Untitled'])`; the backend imports every collection named "Untitled" — both.
- **Verifier's reasoning/confidence:** High confidence. Confirmed the backend matching logic matches the report exactly by reading `app_discovery.go`. Wrote a standalone test creating two synthetic Insomnia workspaces both named "Untitled"; `ReadDiscoveredCollections` returned 2 entries with the identical name, and `ImportDiscoveredCollections(..., ["Untitled"])` imported both (`len(result.Applied) == 2`) when only one was requested. Confirmed the frontend `selectionKey` collision directly in `DiscoveryModal.svelte` (line 47, used at lines 57/114/118). Confirmed there is no per-item preview/disambiguation step in `App.svelte`'s `importDiscoveredCollections()`.

### 4. Value-cell combobox never sets `aria-controls`, unlike the name cell
- **Severity:** Medium
- **Area:** Header name/value autocomplete
- **File:** `frontend/src/lib/KeyValueTable.svelte`
- **Description:** The header name input correctly sets `aria-controls={kv-${index}-name-listbox}` alongside `role="combobox"` and `aria-activedescendant`, matching the id `SuggestionListbox` actually renders. Both value-cell input paths (the variable-overlay value input and the plain value input) set `role="combobox"`, `aria-expanded`, and `aria-activedescendant` but never set `aria-controls`, even though `SuggestionListbox` renders the same predictable id (`kv-${index}-value-listbox`) for them. The ARIA combobox pattern requires `aria-controls` alongside `aria-activedescendant` so screen readers can associate the input with its popup. Since `headers` is the only `KeyValueTable` caller wiring both `nameSuggestions` and `valueSuggestions` with `variableOverlay=true`, this hits the header Value field in the request builder directly — a real assistive-tech regression on the feature under test.
- **Repro steps:** Open the header Value cell for a row with a recognized header name (e.g. Content-Type) with a screen reader / accessibility inspector attached, trigger the suggestion popup by typing, and inspect the input's ARIA attributes: `role=combobox` and `aria-activedescendant` are present but `aria-controls` is absent.
- **Verifier's reasoning/confidence:** High confidence. Read the file directly: name input sets `aria-controls` at line 345; both value-cell inputs (lines 378-395 and 429-442) omit it. Confirmed via grep that `aria-controls` appears exactly once in the file. Confirmed `SuggestionListbox.svelte`'s rendered id format and that `KeyValueTable` passes the matching `idPrefix` for value cells, so a real listbox id exists that simply isn't wired up. Confirmed the `headers` call site in `App.svelte` (lines 8425-8431) hits the affected variable-overlay branch.

### 5. Bypass/NO_PROXY wildcard rule without a dot boundary over-matches unrelated hostnames
- **Severity:** Low
- **Area:** System proxy detection and use
- **File:** `internal/transport/proxy.go`
- **Description:** In `ShouldUseManualProxy`, a bypass rule starting with `*` is turned into a suffix match by doing `ruleHost = strings.TrimPrefix(ruleHost, "*")` and then `strings.HasSuffix(hostname, ruleHost)`. Unlike the leading-dot form (`.example.com`), which enforces a dot boundary, a wildcard rule with no dot right after the `*` (e.g. `*example.com`, a plausible way a user types a bypass/NO_PROXY entry) becomes a bare-substring suffix match — so `*example.com` also matches unrelated hosts like `fooexample.com`, silently routing traffic for those hosts direct (bypassing the configured proxy). This function backs manual-proxy bypass, environment NO_PROXY, macOS scutil ExceptionsList, and the Windows/GNOME OS-read Bypass list, so the bug is reachable from every proxy-bypass path.
- **Repro steps:** Call `transport.ShouldUseManualProxy("http://fooexample.com/", "*example.com")`. Expected: `true` (proxy still used, since `fooexample.com` is unrelated to `example.com`). Actual: `false` (treated as bypassed). For comparison, `.example.com` and `*.example.com` correctly return `true` for the same host.
- **Verifier's reasoning/confidence:** High confidence. Independently reproduced with a standalone test — exact match to the reporter's claimed output. Confirmed root cause via code inspection: the leading `*` is stripped without inserting/requiring a dot boundary, so `HasSuffix` becomes a bare substring-suffix match. Confirmed the dot-prefixed branch doesn't share the flaw since the `.` character itself survives as the boundary. Confirmed all bypass-list callers funnel through this shared function.

### 6. JSON tree view renders a silent empty panel for array-rooted JSON bodies
- **Severity:** Low
- **Area:** Response inspector
- **File:** `frontend/src/lib/workbench/ResponseInspector.svelte`
- **Description:** `boundedJsonTree()` explicitly returns `{ entries: [], truncated: false }` whenever the parsed JSON value is an array. The "JSON tree" toggle button, however, is shown for any truthy `jsonValue` when `kind==='json'`, and a top-level JSON array parses fine and is truthy. So for any response whose body is a JSON array (e.g. `[1,2,3]`, or a typical `GET /items` list endpoint) with a JSON content-type, the button appears, and clicking it swaps the normal pretty-printed body view for a tree panel that renders zero entries and no truncated notice — the user is left staring at an empty box with no explanation.
- **Repro steps:** Send/simulate a request whose response has `Content-Type: application/json` and body `[1,2,3]`. Select the Pretty view — the "JSON tree" button appears. Click it: the body area goes from showing the pretty-printed array to an empty `.json-tree` div with no rows and no message.
- **Verifier's reasoning/confidence:** High confidence. Read the file directly and confirmed all four pieces line-by-line: `boundedJsonTree`'s array short-circuit, `parsedJson()`'s lack of array exclusion, the toggle button's guard not excluding arrays, and the tree-mode template branch having no fallback message for the empty-entries-and-not-truncated case. Confirmed no unit/component tests reference `boundedJsonTree` or "JSON tree" anywhere in the frontend, so this path is untested.

### 7. `updateRequestPreferences` silently drops `maxResponseBytes` on every General-section save
- **Severity:** Low
- **Area:** Preferences UI — General
- **File:** `frontend/src/App.svelte`
- **Description:** `updateRequestPreferences` (used by every toggle/input in `GeneralSection.svelte`: SSL verification, custom CA enabled/path, keep-default-CAs, store/send cookies, timeout) rebuilds the `RequestPreferences` object field-by-field but never copies through `current.maxResponseBytes`. Because `RequestPreferences.MaxResponseBytes` is `json:"maxResponseBytes,omitempty"`, the omitted field marshals as absent/0, and `NormalizeRequest`/`responseBodyReadLimit` treats 0 as "use default." So any pre-existing `maxResponseBytes` value is silently reset to default the next time a user touches the SSL, CA, cookie, or timeout controls in Preferences > General. There is currently no UI control that sets this field, so the loss is silent and not yet user-visible via the UI — but it is a real, reproducible defect that will surface as soon as such a control ships, or any other future caller sets the field.
- **Repro steps:**
  1. Set `preferences.request.maxResponseBytes` to a non-zero value (confirmed live via `internal/core/response_limit_test.go`'s `TestHTTPResponseSurfacesTruncation`, which sets it to 1000 and verifies enforcement).
  2. In Preferences > General, toggle SSL/TLS Certificate Verification (or Store Cookies, Send Cookies, or edit Request Timeout).
  3. Inspect `appState.preferences.request.maxResponseBytes` — it is back to 0/default.
- **Verifier's reasoning/confidence:** High confidence. Confirmed `next` in `App.svelte` (lines 5702-5728) is a fresh object literal with no `...current` spread and no `maxResponseBytes` field. Confirmed every General-section control routes through this function. Confirmed `UpdatePreferences` (backend) does a full state replace, not a field-merge, so nothing preserves the old value server-side. Confirmed `responseBodyReadLimit` explicitly treats 0 as "use default." Ran `TestHTTPResponseSurfacesTruncation` — passed, confirming the field is meaningful when set. Grepped the whole frontend and found no current UI control for this field, confirming the "silent until a control ships" framing is accurate.
