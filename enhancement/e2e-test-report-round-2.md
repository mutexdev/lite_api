## 1. Summary

Round 2 covered the same 15 functional areas as round 1, using the same method: automated Go/frontend test suites, full source reading, and targeted throwaway repro tests, with regression checks layered on top for each of round 1's seven fixes.

- **Regression data was provided for 6 of the 7 round-1 fixes.** Round 1's issue #3 ("discovered collections selected/imported by name only") has no corresponding regression entry in this round's results — see the regression table below for detail on the mapping.

This is flagged as **not holding**, not softened.
- **3 new issues were confirmed** by independent re-verification: 1 high, 1 medium, 1 low. The high-severity one is a direct escalation of the same rollback gap called out above.
- **0 reported issues were rejected** by the skeptical verifier this round — every issue that was reported was confirmed, consistent with round 1.

## 3. New confirmed issues

Grouped by area, most severe first.

### 3.1 Batch-level rollback discards the imported global environment from memory but leaves its file on disk, so it silently reappears on the next state read
- **Severity:** High
- **Area:** Postman environment/globals import and its apply-path rollback
- **File:** `internal/core/collection_import_apply.go`
- **Description:** `applyImportedGlobalEnvironmentsLocked` writes the imported environment to disk and appends it to the live `workspace.GlobalEnvironments` slice before `ApplyCollectionImport`'s batch-commit step runs. When that environment import succeeds but a different candidate in the *same batch* fails at the final `persist()` step, the code takes the `a.state = before` rollback path. `rollbackCollectionImportMutations` only tracks collection-folder filesystem operations — the environment file write is never added to its mutation list, so the already-written `.yml` is never removed from disk. `a.state = before` correctly wipes the environment from memory at that instant, but the very next ordinary call into the app (including a plain `GetState()`) runs `ensureReadyLocked()` → `prepareWorkspaceGlobalEnvironmentsLocked()`, which re-reads the `environments/` directory from disk and merges anything found there — including the orphaned file — back into `GlobalEnvironments`. A "failed" import that the caller was told was fully rolled back comes back with its original ID on the next read.
- **Repro:** Build a batch with one Postman-environment source and one ordinary collection source, in a single `ApplyCollectionImport` call. Force the batch's final `persist()` to fail after individual candidate writes have already succeeded. Observe `ApplyCollectionImport` returns an error and, immediately after, in-memory `GlobalEnvironments` is empty as expected. Then call `GetState()` (or anything else that runs `ensureReadyLocked`) and observe the imported global environment is back, with its original minted ID, even though the caller was told nothing was kept.
- **Verifier's reasoning:** Independently reproduced against the current tree with a purpose-built test (removed afterward; `git status --porcelain` confirmed clean). Confirmed the mechanism by reading `collection_import_apply.go`, `app_env_secrets.go`, and `app_bootstrap.go`. One part of the original report was overstated and corrected in verification: the resurrecting `GetState()` call does not itself set `changed=true` and force an immediate `state.json` rewrite — the in-memory resurrection is immediate and confirmed, but the on-disk `state.json` rewrite only happens on a subsequent state-changing operation, not necessarily that exact call. The core defect — silent, ID-preserving resurrection of a supposedly-rolled-back environment — is real, reproducible, and matches the title precisely; severity high is appropriate given the trust/data-integrity implications of a "failed" import silently succeeding.

### 3.2 `CreateFolder` rejects any root folder name that merely *contains* "environments", not just the exact reserved name
- **Severity:** Medium
- **Area:** Collection tree operations — create/rename/delete/clone folders and requests
- **File:** `internal/core/app_tree_crud.go`
- **Description:** The reserved-name guard for root-level folders uses `strings.Contains(strings.ToLower(strings.TrimSpace(directoryName)), "environments")` instead of an exact-match comparison. The sibling reservations for "collection" and "folder" elsewhere in the same file correctly use `strings.EqualFold`. As written, any root-level folder name that merely contains the substring "environments" — e.g. "My Environments Archive", "environments-backup", "OldEnvironmentsDump" — is incorrectly rejected, even though only the literal name "environments" collides with Bruno's on-disk convention.
- **Repro:** Call `app.CreateFolder(collectionID, "", "My Environments Archive", "My Environments Archive")` on a freshly created collection's root. The call fails with `the folder name "environments" at the root of the collection is reserved in bruno`, even though the intended directory name is not literally "environments".
- **Verifier's reasoning:** Confirmed the exact `strings.Contains` usage at `app_tree_crud.go:126-127`, contrasted against `strings.EqualFold` used at the sibling reservation sites (lines 208, 466, 611, 711). Confirmed `bru.SanitizeName` does not strip or alter the substring "environments" from such names, so nothing else neutralizes the bug before the check runs. Independently wrote and ran a fresh regression test directly against the real `CreateFolder` API — reproduced the exact same error string reported.

### 3.3 JSON tree panel shows contradictory messages when a single root field exceeds the size budget
- **Severity:** Low
- **Area:** Response inspector
- **File:** `frontend/src/lib/workbench/ResponseInspector.svelte`
- **Description:** `boundedJsonTree()` checks the byte budget before pushing each entry, so if the very first root-level entry's serialized text alone exceeds `JSON_TREE_BUDGET` (96KB), the function returns `{entries: [], truncated: true}` — zero entries, but truncation occurred. `ResponseInspector.svelte` gates its two explanatory messages with independent, non-exclusive `{#if}` blocks: one for `entries.length === 0` ("This response has no fields to expand.") and one for `truncated` ("Tree render is bounded to 100 root items and 96 KB."). When both conditions are true at once, both messages render together — directly contradicting the commit's own stated goal that "'nothing to show' and 'stopped early' read differently."
- **Repro:** Load a JSON response whose body is an object with one root key whose value serializes to more than 96KB (e.g. `{"blob": "<100KB of text>"}`). Switch to Pretty view, click the "JSON tree" toggle, and observe both the empty-panel message and the truncation message rendered together.
- **Verifier's reasoning:** Reproduced directly by running the reporter's exact `boundedJsonTree` repro, which printed `{"entries":[],"truncated":true}` as claimed. Confirmed both `{#if}` blocks in `ResponseInspector.svelte` are independent (not if/else) and both fire under this state. Confirmed no existing test in `jsonTree.test.mts` exercises the single-first-entry-exceeds-budget case — the existing budget test spreads the payload across several entries, so this combination was never caught. Confirmed commit `41c7b32`'s message matches the quoted intent. Severity low is reasonable — cosmetic/contradictory UI text, not data loss or a crash.
